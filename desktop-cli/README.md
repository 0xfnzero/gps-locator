# GPS Locator ADB CLI

Controls one or many Android QA devices through ADB. The Android receiver requires the system `DUMP` permission, so ordinary installed apps cannot issue lab commands.

```bash
npm test
node gps-lab.mjs prepare --serial all --apk ../app/build/outputs/apk/debug/app-debug.apk
node gps-lab.mjs status --serial all
node gps-lab.mjs set --serial emulator-5554,qa-phone-02 \
  --lat 40.757955 --lon -73.985532 --name "New York QA" \
  --time-zone America/New_York
node gps-lab.mjs scenario --file scenarios/delivery-route.example.json --serial all
node gps-lab.mjs scenario --file scenarios/route-completion-smoke.example.json --serial all
node gps-lab.mjs suite --file suites/global-release-smoke.example.json --dry-run
node gps-lab.mjs suite --file suites/global-release-smoke.example.json \
  --serial all --output reports/global-release-smoke
node gps-lab.mjs report --output reports --serial all
npm run control-center
```

The `prepare` command grants location access and selects GPS Locator as the mock-location app through AppOps. GPX, KML, and the app route JSON schema are accepted by the `route` command.

The `status` command prints one JSON line per connected device with the installed app version, product tier, app-scoped device ID, mock-location readiness, active-simulation state, optional license summary, stable `readiness` code, and `commandReady` boolean. A missing app or receiver failure is retained as `available: false` for that serial instead of hiding other connected devices. Add `--require-ready` in CI to emit every record and then exit nonzero when any selected device needs setup or has unavailable status; an already active simulation remains command-ready. Status and device-ID broadcasts are read-only, protected by Android's signature-level `DUMP` permission.

`--serial` accepts `all`, one serial, or a comma-separated subset such as `emulator-5554,qa-phone-02`. This same subset selection is available in the control center. The `set` command and Quick location form accept an optional validated IANA time zone. A standalone quick/static command intentionally leaves that time zone active with the mock location; use a suite when the original device time zone must be captured and restored automatically.

JSON scenarios are validated before any device is changed. Coordinates, route speed (0.5-500 km/h), waypoint stops (0-86400 seconds), and distinct route points must match the Android route model, so an invalid batch fails locally instead of partially starting across a device fleet.

Reports are generated by the app and pulled from each device as schema-version-2 JSON. They include app/device metadata and timestamped static/route simulation events, including the actual time-zone ID and UTC offset observed when each run started.

The CLI `stop` command waits until Android confirms the mock-location foreground service has exited. The control center then automatically pulls the finalized schema-v2 report from every selected device and writes `fleet-summary.json`, `fleet-results.junit.xml`, and `devices/*.json`. Suite and fleet-command summaries appear together under Recent runs and expose safe JSON/JUnit downloads from the report detail panel. Fleet JUnit treats only `stopped` or `completed` events as successful, so a stale `running` event catches a stop/report race. A partial pull remains visible as a failed Fleet summary instead of hiding the successful stop or silently dropping evidence.

Control commands briefly bring GPS Locator to the foreground before starting a location simulation. Android 12 and newer block location foreground services launched directly from a background broadcast; the CLI handles this requirement automatically. Labels are Base64-encoded in transit, so spaces and non-Latin names are preserved.

## Team scenario suites

Version scenario files and suite manifests with the application or QA repository. The local schemas under `schemas/` provide editor completion for both formats. A suite manifest uses relative scenario paths so the same checkout runs in CI and on every operator workstation:

```json
{
  "$schema": "../schemas/suite.schema.json",
  "schemaVersion": 1,
  "name": "Global login and delivery release smoke",
  "steps": [
    {
      "id": "us-login",
      "scenario": "../scenarios/login-country.example.json",
      "holdSeconds": 5,
      "stopAfter": true
    }
  ]
}
```

Static and route scenarios can declare an IANA time zone alongside their coordinates:

```json
{
  "schemaVersion": 1,
  "type": "static",
  "name": "New York local-time login",
  "timeZone": "America/New_York",
  "latitude": 40.757955,
  "longitude": -73.985532
}
```

Before a time-zone-aware suite changes any device, the CLI reads the original system time zone for every target. It applies and verifies each declared zone through the authorized ADB shell, records the requested zones in the suite reports, then restores every original value after scenario execution and report collection. A capture or restoration failure makes the suite fail and appears as a device-environment JUnit case. Scenarios without `timeZone` leave the current zone unchanged; the suite still restores the pre-suite value at the end. A standalone `scenario` command intentionally leaves its declared time zone active together with its mock location.

`holdSeconds` keeps the simulated point or route active before moving to the next step and is limited to 0-3600 seconds. `stopAfter` defaults to `true`, which closes the run cleanly before the next shared scenario. Set it to `false` only when the final state must remain active for a separate test runner.

`suite --dry-run` compiles every referenced scenario without invoking ADB, making it suitable for pull-request checks. A normal suite also validates every step before discovering devices. Runtime failures are isolated per device; after all possible work finishes, the command writes `suite-summary.json` and `suite-results.junit.xml`, pulls each device's app report into `devices/`, and exits nonzero when any device command or report pull failed.

The JSON summary records suite and scenario SHA-256 values, timing, each step's delivery/stop outcome, and report paths. The JUnit document represents every step/device pair and report pull as a CI test case, including command failures and traceability metadata. Jenkins, GitHub Actions, GitLab CI, and other standard test-report publishers can ingest it directly. `completed` means the Enterprise receiver accepted the commands and cleanup/report collection succeeded; application-specific assertions still belong in the team's UI/API test runner.

Configure the CI job to retain the full output directory and publish `**/suite-results.junit.xml` as a JUnit test report. Keep `suite-summary.json` and `devices/*.json` as build artifacts for detailed diagnosis and source-hash traceability. The CLI writes both report formats before it exits nonzero, so failed fleet runs remain visible to the publisher.

## Local control center

Run the operator UI from the same workstation that owns the authorized ADB session:

```bash
npm run control-center
```

It opens `http://127.0.0.1:43821/` and provides connected-device subset selection, per-device version/license/mock-location readiness, local copying of selected app-scoped device IDs for license issuance, one-click preparation of the selected devices, validated Quick location delivery with optional IANA time zones, suite validation, fleet execution, live command output, stop-and-collect controls, and recent Suite/Fleet report inspection and JSON/JUnit download. Preparation grants the app permissions and selects it for mock locations, executes independently per serial, then verifies readiness again. A status-unavailable device remains selectable so an operator can still attempt preparation or other diagnostics; the Web API never accepts an APK path. Full device IDs are copied only after an explicit local action and are not sent to a server or written into run reports. Suite manifests are discovered only under `suites/`; reports are written under `control-center-reports/`. Override those locations when a team keeps suites and retained results elsewhere:

```bash
node control-center.mjs \
  --suite-dir /absolute/path/to/team-suites \
  --report-dir /absolute/path/to/retained-results
```

The control center intentionally listens only on `localhost`, `127.0.0.1`, or `::1`. Mutating API calls require a per-process control token and same-origin JSON requests. It does not accept client-supplied suite paths or shell commands, and it prevents overlapping suite runs. Use the CLI directly for headless CI; use `--no-open` when starting the control center without launching a browser.

## Optional signed licenses

Generate a private RSA key once and keep it outside the repository:

```bash
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out enterprise-private.pem
node license-tool.mjs --private-key enterprise-private.pem --print-public-key
```

Set the printed value as `GPS_ENTERPRISE_LICENSE_PUBLIC_KEY` when building the enterprise APK. Issue a signed license with:

```bash
node license-tool.mjs --private-key enterprise-private.pem \
  --license-id customer-001 --organization "Customer QA" \
  --expires 2027-12-31 --output customer-001.license.json
```

Omitting `--device-id` creates a team license compatible with existing installations. For per-device licensing, read the Android ID from the target device and include it in the signed license:

```bash
DEVICE_ID=$(node gps-lab.mjs device-id --serial SERIAL --plain)
node license-tool.mjs --private-key enterprise-private.pem \
  --license-id device-001 --organization "Customer QA" \
  --device-id "$DEVICE_ID" --expires 2027-12-31 \
  --output device-001.license.json
```

Device-bound licenses use schema version 2 and include the normalized Android ID in the RSA-signed payload. They remain valid across reinstallations signed with the same app key on the same Android user/device, but not after a factory reset, user-profile change, signing-key change, or transfer to another device.

Use `gps-lab device-id` or the copy action on the app's Enterprise license screen. Do not substitute `adb shell settings get secure android_id`: Android 8 and newer scope this identifier to the app signing key and user, so the shell can observe a different value. The device-ID receiver is protected by Android's signature-level `DUMP` permission and does not require an existing license, allowing first-time provisioning from an authorized ADB shell.

To issue a device batch, select the target fleet in the control center and use **Copy device IDs**. The copied rows are `serial<TAB>app-scoped-device-id`, which can be passed directly to the offline batch issuer:

```bash
node license-tool.mjs --private-key enterprise-private.pem \
  --organization "Customer QA" --expires 2027-12-31 \
  --devices-file customer-devices.tsv \
  --license-id-prefix customer-2027 --output-dir customer-licenses
```

The batch is fully validated before its output directory is created. Duplicate serials or device IDs, malformed rows, ambiguous generated names, invalid payloads, and existing target files reject the batch. Each generated schema-v2 license is verified with the public key derived from the private key before it is written. Files use mode `0600`; `license-manifest.json` records the organization, expiry, public-key SHA-256 fingerprint, serial/license mapping, and SHA-256 of each exact license document. The complete mapping is also RSA-signed under a separate manifest domain so serial assignments cannot be altered without detection.

The receiving administrator can verify a delivery without access to the private key. `--public-key-file` accepts either the Base64 DER printed by `--print-public-key` or an SPKI PEM public key:

```bash
node license-tool.mjs \
  --verify-manifest customer-licenses/license-manifest.json \
  --public-key-file enterprise-public-key.txt
```

Verification checks the public-key fingerprint, manifest signature, safe relative file names, unique device mappings, exact document hashes, manifest/license field agreement, every license signature, and every device binding. Keep the manifest and licenses in the customer delivery record, but handle them as customer device data. The private key is never copied into the output directory and is not accepted by verification mode.

The customer imports the license file from the app settings. ADB commands work without a license; signed licenses are optional for teams that want to identify devices.
